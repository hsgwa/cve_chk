# 運用の手引き

本番の環境で使う前に確かめること、対象のサーバーへの影響、回収物の扱い、レポートを使った対応の流れ、困ったときの対処をまとめます。操作の詳細は [README](../README.md)、仕組みは [DESIGN.md](DESIGN.md) を参照してください。

## 1. 本番の前に確かめること

1. **検証機で 1 台ずつ回収する。** 本番と同じ構成（OS、入っている製品、ディスクの大きさ）の検証機で回収スクリプトを実行し、次を記録します。
   - 所要時間（`collect.log` の最後の行、`os_info.json` / `inventory.json` の `duration_sec`）
   - CPU とメモリの使用量（Linux は別の端末で `top -p $(pgrep -d, syft)`、Windows はタスクマネージャー）
   - 業務処理への影響（応答時間、バッチの所要時間）
2. **回収した内容が実態と合っているか確かめる。** `vuln-triage check-inputs` で環境ごとのコンポーネント数と注意事項を見て、主要な製品（Java、HULFT、DataMagic、Web サーバーなど）が出ているかを確かめます。出ていなければ走査範囲（Windows の `-ScanRoots`、Linux の `SCAN_ROOT`）や個別製品の表を直します。
3. **会社公表リストが正しく読めるか確かめる。** `vuln-triage check-inputs --advisory <リスト>` で通達の件数と警告（読まなかったシート、結合セル、読めない CVE 番号）を確かめ、通達の製品名が回収データのどれに当たるかを見ます。当たらない製品名は `config.yaml` の `aliases` に登録します。
4. **環境マスタに対象のホストをすべて登録する。** 回収し忘れたホストは「判定不能（回収漏れ）」として出るので、漏れに気づけます。

## 2. 対象のサーバーへの影響

| 項目 | 内容 |
|---|---|
| 変更 | しない。パッケージのインストール、設定、サービスの変更はしない。ネットワークも使わない |
| 書き込み | 出力先（`out/<ホスト名>/`）に数十 KB〜十数 MB。Linux は syft の展開先（`.syft_work`）に一時的に約 60 MB（終われば消す） |
| ディスクの読み込み | 最も大きい負荷。Linux は `/` 全体、Windows は走査対象のフォルダのファイルを読む |
| CPU | syft は複数のコアを使う。Windows のスクリプトはほぼ 1 コア |
| メモリ | syft は、ソフトの多い環境で数百 MB〜1 GB 程度を使うことがある（環境による。検証機で測ること） |
| 優先度 | 既定で最低（Linux: `nice -n 19`、`ionice -c3`。Windows: 通常以下）。業務処理が優先される |
| 打ち切り | Linux は syft が 3 時間で終わらなければ打ち切る（`SYFT_TIMEOUT_SEC`）。中断しても途中の結果が残るだけで、サーバーには何も残らない |
| 権限 | Linux は root、Windows は管理者を推奨（読めないフォルダの中身が漏れるため）。読み取りだけを行う |

実測した所要時間（2026-11 時点）:

| 環境 | 所要時間 |
|---|---|
| Windows 11（Program Files など 7 万ファイル） | 55 秒 |
| Ubuntu 24.04（開発ツール一式が入った大きな環境。初回） | 18 分 |
| 同じ環境の 2 回目（ファイルがキャッシュに残っている） | 3 分 |
| Amazon Linux 2 / 2023（最小構成） | 1 台 20 秒前後 |

負荷を抑えたい場合は、業務の少ない時間帯に実行するほか、Windows は `-SkipDll`（dll を読まない）が使えます。Linux で走査範囲を狭めると OS パッケージの一覧が取れなくなることがあるので、範囲は狭めずに時間帯で調整してください。

## 3. 回収物の扱い

回収物（`out/<ホスト名>/`）とレポートには、ホスト名、インストールされているソフトの一覧と版、ファイルのパス、適用済みの更新プログラムが入ります。**攻撃者にとって有用な情報なので、社内の機密情報として扱ってください。**

- 回収物の持ち出し・保管は、社内の手続きに従う。
- 管理 PC では、回収物とレポートを置くフォルダの権限を担当者だけに絞る。
- 不要になった回収物は消す（再判定に使う最新の 1 回分だけを残す、など）。
- このツールが外部に送るのは次だけです。回収物そのものは送りません。
  - `db-update`: 取得するデータの名前（Maven、Ubuntu など）
  - Windows OS の判定: 通達の CVE 番号（MSRC へ）
  - `--resolve-hashes`（既定では使わない）: 名前の分からない jar の SHA-1（Maven Central へ）

## 4. 管理 PC の運用

- **脆弱性データは毎日更新する。** `register_daily_task.ps1` でタスクを登録します。ログオフ中も動かすなら `-NoPassword`（管理者として登録）か `-RunWhetherLoggedOn` を使います。更新が 1 日を超えて古いと、`run` の結果に警告が出ます。
- **データの置き場所には 2 GB 以上の空きを用意する**（Ubuntu・npm・Debian を含めると索引だけで 1 GB を超える）。
- データのファイルが消えた場合（ウイルス対策ソフトや一時ファイルの掃除など）は、`run` が「データベースのファイルがありません」で止まります。`vuln-triage db-update` を実行すると、消えたデータは全件を取り直して元に戻ります。データの置き場所は、`%TEMP%` のような自動で掃除される場所にしないでください。
- **ウイルス対策ソフトが、検証用に置いた脆弱な jar（log4j-core 2.14.1 など）を隔離することがあります**（検証機で確認）。本番のサーバーでは、隔離されたファイルは回収されません。

## 5. レポートを使った対応の流れ

1. **サマリ** で、総合判定の件数、注意事項（回収漏れ、古いデータ、照合できなかったもの）を確かめる。注意事項がある場合は先に解消する。
2. **要更新パッケージ** で、環境ごとに更新するパッケージと「この版以上に更新」を確かめ、ランクと期限の順に対応する。1 行の更新で、その行の脆弱性がまとめて直る。
3. **通達別一覧** で、会社公表の通達ごとの総合判定を確かめ、回答に使う。「判定不能」の環境は、理由（明細の備考）を見て回収をやり直すか、手で確かめる。
4. **明細** は、通達 × 環境 × パッケージのすべての判定の証跡として保存する。
5. 対応したら、回収し直して再実行し、影響ありが消えたことを確かめる。

「影響あり」は版が一致したという意味で、実際に攻撃できるかどうか（設定で無効になっている、該当の機能を使っていない、など）は判定しません。必要に応じて人が判断してください。

## 6. 困ったとき

| 症状 | 原因と対処 |
|---|---|
| `run` が「脆弱性データがありません」 | `vuln-triage db-update --inventory-dir <回収データ>` を先に実行する |
| 「脆弱性データの更新が古くなっています」 | タスクが動いているかを `logs\db-update_<日付>.log` で確かめる。手で `db-update` を実行する |
| 「脆弱性データが無いため照合していないもの」 | 回収データに新しい種類のパッケージがある。`db-update --inventory-dir <回収データ>` で取得する |
| 環境の判定がすべて「判定不能」 | 回収ファイルが読めていない。`check-inputs` で注意事項を見る（回収フォルダが無い、syft の失敗、収集の中断など） |
| Linux の回収で「syft が … 秒で終わらず打ち切りました」 | `SYFT_TIMEOUT_SEC` を延ばすか、`EXTRA_EXCLUDES` で大きなデータのフォルダを外す |
| Linux の回収で「syft を実行できません」 | 展開先が noexec。`WORK_DIR` で別の場所を指定する |
| Windows の回収で jar・exe が 0 件 | 走査対象に入っていない。`-ScanRoots` で指定するか `-AllDrives` を付ける。「スキャン範囲外で動作中」に出ているパスを確かめる |
| 通達の製品が「未使用」になるが、実際は入っている | 名前の表記が違う。`check-inputs --advisory` で確かめ、`aliases` に登録する |
| Windows OS の判定が行われない | MSRC に接続できない。管理 PC から `api.msrc.microsoft.com` に接続できるか確かめる。`--offline` ではキャッシュだけを使う |

終了コード: `vuln-triage run` は正常に終われば 0、入力やデータの誤りで 2。`db-update` は一部のデータの更新に失敗すると 1（前回のデータは残る）。`collect_linux.sh` は syft が失敗すると 3（`os_info.json` は出る）。
