# 不具合の記録と類似不良の担保

開発中に見つけて直した不具合について、次の3点をまとめた記録です。
- どうすれば早く検出できたか
- 同じ種類の不具合が他に無いことをどう担保しているか
- 再確認の手順

記録日: 2026-11-20

## 2. どうすれば早く検出できたか

| 見逃した原因 | 該当 | 検出できた方法 | 今回入れた担保 |
|---|---|---|---|
| **正解と比べていなかった**。自分の実装の結果だけを見ていた | 8〜11、15、16、19 | 同じ入力を他のツール（Trivy・Grype・OSV-Scanner）にかけ、差分を1件ずつ調べる | 4 ツール比較の手順（[COMPARISON.md](COMPARISON.md)）。データ源や判定を変えたら再実行する |
| **対象環境の実際の構成で試していなかった**。Amazon Linux 2 の標準カーネル（5.10）、Ubuntu の universe、RHEL 10、Alpine の版の形を試験データに入れていなかった | 15、18、22〜24 | 利用者の環境（EC2 / EMR の AL2 + kernel 5.10 など）を代表する SBOM を試験データに入れる | kernel 5.10 の検証用 SBOM と extras のテスト。Ubuntu Pro・RHEL 10・Alpine のテスト |
| **外部データの仕様を網羅的に確かめていなかった**。データに含まれる系統の種類を一覧で見ていなかった | 15、18、22、23 | データに現れる系統（エコシステム名）をすべて列挙し、使うか使わないかを1つずつ決める | 系統の分類（`vulndb/coverage.py`）。分類外の系統が現れたら `db-update` が警告し、監査が NG にする |
| **不変条件を検査していなかった** | 8、13、24、25 | 「検出のもとの記録にそのパッケージが載っている」「影響範囲の下限 ≦ 修正版」などを全データで機械的に確かめる | 監査スクリプト `tools/audit_vulndb.py`（C、D1〜D5） |
| **同じ処理が複数箇所にあった**。PURL の読み取り、版の比較規則の決め方 | 9、27、28 | 処理の入口を 1 つにし、それ以外で同じことをしていないかを機械的に調べる | `purl.py` に一本化。静的な検査（`tests/test_static_checks.py`） |
| **組み合わせを網羅していなかった**。オプション、セルの型 | 20、31 | オプションやセルの型の組み合わせ表を作り、すべてテストする | `db-update` のオプションの組み合わせのテスト、Excel のセルの型 × 項目のテスト |
| **実行環境で試していなかった**（Windows PowerShell 5.1） | 1、17、30 | 実機で実行する | 誤りやすい書き方（`2>&1` の後の扱い、`Write-Host` の連結、List の `@()`）の静的な検査。**実機での確認は引き続き必要** |
| **黙って処理を飛ばしていた**（照合できない種類のパッケージ） | 5、11 | 飛ばしたものを件数で出し、合計が合うか確かめる | 照合の対象外を「収集状況」に件数で出す。監査 D4 で「照合した＋理由つきで外した＋データ無し＝全件」を確かめる |

## 3. 類似不良の担保（現在の検査）

| 不具合の種類 | 検査 | いつ | 結果（2026-11-20、実データ） |
|---|---|---|---|
| 情報が別の系統にしか無い | 監査 A: 系統をすべて分類できるか | `db-update` のたび（警告）、監査 | 954 系統（Ubuntu・Debian・Amazon・RHEL・Rocky・Alma・Alpine・ライブラリ）すべて分類済み |
| 同上（Amazon Linux 2） | 監査 B: extras の全トピックを取得済みか。extras が無いまま照合したら「判定不能」にする | 監査、`run` のたび | 73 / 73 トピック |
| 版の比較規則 | 監査 C: データ中の版を規則で読めるか、下限 ≦ 修正版か | 監査 | 全エコシステムで順序の矛盾 0。読めない版は PyPI の 0.2%（`1.6.0-NA` など）だけ |
| 記録内の別要素の誤適用 | 監査 D1、静的な検査 | 監査、テストのたび | 違反 0（検出 17,000 件超） |
| ID の対応付け | 監査 D2 | 監査 | 違反 0 |
| ヘッダ等への誤適用 | 監査 D3。Trivy・Grype の扱いを実データで確認（Ubuntu の `linux-headers-*` / `linux-libc-dev` は両者とも外す。Amazon の `kernel-headers` 等は両者とも検出） | 監査 | 違反 0 |
| 黙って抜ける | 監査 D4、「収集状況」への表示 | 監査、`run` のたび | 5,612 件 = 照合 5,324 + 理由つきで外した 288 + データ無し 0 + 理由なし 0 |
| PURL の読み落とし | 監査 D5、静的な検査（読み取りは `purl.py` だけ） | 監査、テストのたび | v2 以降の Go モジュール 353 件すべて subpath 付き |
| 版の比較の入口 | 静的な検査（`packaging` は比較モジュールだけ） | テストのたび | 違反 0 |
| PowerShell の書き方 | 静的な検査 | テストのたび | 違反 0 |
| ファイル名・オプション・セルの型 | テスト | テストのたび | 全件パス |
| 判定の総合的な正しさ | 4 ツール比較 | データ源・判定を変えたとき | 他の 3 ツールがそろって検出し本ツールだけ無いもの 0 件（修正前後で数字の変化なし） |

## 4. 対象外として残しているもの（理由つき）

監査 A で「理由つきで使わない」に分類した系統のうち、利用者の環境によっては見落としにつながるものです。

| 系統 | 理由 | 影響を受ける環境 |
|---|---|---|
| RHEL の追加製品（OpenShift、JBoss、Satellite など） | 別契約のリポジトリで、追加製品ごとに系統が分かれる | RHEL でこれらの製品を使うホスト |
| RHEL の延長サポート（EUS / E4S / AUS） | 通常の RHEL は `enterprise_linux` の情報で判定する | マイナー版を固定した RHEL |
| Ubuntu の FIPS / Realtime / BlueField | 特定製品向けのカーネル・暗号ライブラリ | FIPS 版、Real-time Ubuntu を使うホスト |
| Amazon Linux 2 の extras の arm64 | x86_64 の情報を使う（同じ版番号のため） | Graviton（arm64） |

## 5. 再確認の手順

```
pytest -q                                                     # 静的な検査とテスト
python tools/audit_vulndb.py --db-dir vulndb --inventory-dir inventory   # 実データの監査（問題があれば終了コード 1）
```

データ源や判定方法を変えたときは、加えて [COMPARISON.md](COMPARISON.md) の手順で 4 ツール比較を再実行し、「本ツールだけ無い」が 0 件のままであることを確かめます。
